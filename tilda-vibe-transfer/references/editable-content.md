# Editable content and repeated groups

Before transfer, map what is editable, where it lives in the source DOM, which group it belongs to, and how to verify it in Tilda. Include headings, descriptions, labels, links, images with suitable alt text, and meaningful content for each repeated item. Do not promise a separate field or operation before verifying it in the interface.

For each collection—slides, tabs with panels, cards, accordions, and others—prepare a consistent group containing all content for one item. Prefer semantic markup with actual text, links, and images in HTML: do not hide the only source of content in a JavaScript array or generate it exclusively with scripts. Avoid fixed item counts and indexes. Scripts derive the number of groups from the DOM, correctly associate tabs and panels, and update counters, navigation, and accessible states when items are added or removed. Check zero, one, and multiple items where those states are valid for the component; preserve keyboard interaction.

Adapt nesting and supporting attributes only as needed without renaming source classes. Do not assume any single markup pattern guarantees Tilda recognition: check the editor structure and available operations in the real interface. If a new group can be added but fields belong to another group, fail to save, or break behavior, revise and recheck. If Tilda does not offer an operation, explain the concrete limitation and agree on an approach with the user; do not claim the requirement is met.

In one verified project example, consistent slide groups contained all four images and JavaScript assigned the active state; the editor allowed duplication of the group in ITEMS. This is a hypothesis to test, not a universal Tilda schema. Do not add a special initial state class to only one group if it prevents the editor from recognizing consistent groups; obtain agreement before changing an existing source class.
